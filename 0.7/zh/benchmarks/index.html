    基准测试¶

    英文版本为准

    本页译自英文，由模型翻译。若与英文原文存在差异，以英文原文为准。

    这个 crate 位于 zeromq 客户端和你的服务之间：一个产出消息的订阅、一份文档化的帧布局、一个把它 写出去的发布者。框架的运行时又在这之上。这一页说明这两层各自花了多少，参照物是同样的活用客户端 手写一遍。

    每个场景在同一个进程里跑三遍，三个循环之间只差一件事：由什么来搬运消息。

    • 裸客户端 - 直接驱动 zeromq 套接字：绑定、接收、解码。
    • ruststream-zeromq - 这个 crate 的订阅、它产出的消息、它的 ack 和它的发布者，由基准测试 里的一个循环来驱动：没有处理器、没有应用、没有分发。
    • RustStream 服务 - 用户会写的那整个服务，#[subscriber] 加上应用，跑在同一个 crate 上。

    「crate 的开销」是第二列对第一列：这个 crate 在它所包装的套接字之上要花多少，这个仓库要为这个 数字负责。「总开销」是第三列对第一列，于是两者之差就是运行时。运行时属于核心 crate，它在自己的 仓库里以每条消息的指令数和分配数来度量；这两列补上的是运行时在这一个传输上的代价。

    其余一切都保持相同：套接字的模式、套接字选项、线上的三个帧、解码成同一个类型、载荷字节、tokio 运行时和构建。这套流程属于框架本身，写在 RustStream 基准测试页 上；这一页公布它在这台机器上得出的结果。

    这一行里没有 Broker¶

    框架里其他每个 crate 都拿自己和一台服务器相比：起一个容器，客户端连上去，这一行说的是这个 crate 在那个客户端之上多付了多少。ZeroMQ 没有服务器。对端彼此直接讲话，所以每个循环的另一侧都是同一个 进程里的一个套接字，没有什么要起、也没有什么要停。

    这让这一行回答的是另一个问题，而不是把原来的问题答得更快或更慢。路上没有服务器的传输，每条消息 都很便宜，于是这个 crate 自身的活在总数里占的比重比别处都大。把这里的百分比和别的 crate 放在 一起看，只在记住这一点的前提下才有意义。

    数字¶

    三个交错轮次中的最佳值，括号里是中位的一轮。速率那几列越大越好。

    表格由浏览器从上一次运行写下的文档读出，所以这一页上没有任何会过期的副本。

    两个场景都是 PUSH/PULL 模式，跑在这个 crate 允许的两种传输上：回环地址上的 tcp:// 和 ipc://。它们只差在一条消息走过内核的路径，别的都一样，所以两个放在一起就能看出其中有多少 代价落在套接字上。

    标为「无法区分」的开销，小于它所比较的那两列各自多次运行之间的离散范围。低于这个范围的数字读 起来像是从未测到过的精度，所以不公布。

    这里没有哪一行带着「受传输限制」的标记，这是模式本身的性质，不是机器的性质。这个标记说的是：一次 投递的大部分时间都花在等传输上，它上面的活就做在这段本来就要付的等待里面。PUSH/PULL 不给一次 投递任何可等的东西：消费者从流里读帧，什么也不回送，没有轮询、没有拉取、也没有确认，所以一次 投递要花零次往返，这个标记无从谈起。

    下面和机器一起公布的往返时间，是同一个传输上两个对端之间一次交换的代价，用一对 REQ/REP 套接字在 三个循环之外测得。把它乘以上面那个零，再和每条消息的时间比一比：标记就是从这个算式来的，你可以 自己验算。

    同一次运行的机器可读形式在 benchmarks/results.json， 框架的站点用它拼出跨 Broker 的汇总表。

    crate 自身的代码¶

    第二张表是这个 crate 自身在每条消息上的开销，是数出来的，不是计时得来的：指令数由 callgrind 统计， 内存分配次数由 DHAT 统计。每个场景都是用户会写的那种服务，跑在生产环境的 Broker 上，绑定在回环地址的 一个 TCP 端口上。另一端是一个在自己线程上的对端：一个裸 zeromq 套接字，按这个 crate 的三帧布局写消息。

    计入的是服务线程做的全部工作：框架的分发和编解码器，这个 crate 的订阅、帧布局和发布者，以及 zeromq 客户端在这个线程上的分帧和套接字处理。对端的线程不计入，内核也不计入。

    对端在计数开始之前、服务还没有读取的时候写完所有消息，这些消息在内核的套接字缓冲区里等着。PUSH/PULL 会为一个暂时不读的消费者留住它们，所以两行消费场景都用它。一个 PUSH/PULL 端点承载一条工作流， 所以回复那一行用的是 DEALER/ROUTER：回复沿着请求进来的那条连接回到发出请求的对端。这一行的计数一直 持续到对端读完所有回复。

    指令数和分配次数都是稳态下每条消息的值：1000 次投递的运行和 2000 次投递的运行之间的斜率。 最后一列是启动服务、接受对端的连接并处理第一次投递一次性付出的开销。这些数字是绝对值，框架自身的开销 也算在内；框架单独的开销由核心库在它的基准测试页面上公布。

    同一个二进制文件跑三次，消费那一行的指令数完全相同；另外两行的总数相差不到三分之一个百分点，因为对端 读取回复的时机和凑满一批的截止时间都取决于时间。分配次数最多相差一个块。just bench-code 在分配次数 超过场景声明的下限时失败，这个下限是这几次运行里的最大值再加百分之零点一；加上 --baseline=main 时， 指令数多出百分之二以上也算失败。改变开销的合并请求要附上自己的数字。

    机器¶

    zeromq crate 既不提供高水位，也不提供缓冲区设置：一个套接字只有对端身份和连接超时，别的都 没有。所以每个循环都用默认选项打开套接字，限制队列的是传输自己的缓冲区。再没有别的可调，所以 除了传输本身，也没有别的套接字配置可以公布。

    构建标志和数字一起公布，因为它们会改变这些数字。用 -C target-cpu=native 构建出的二进制给出的 结果，换一台机器就复现不了，所以这条 recipe 在构建前先把这个变量清空。

    这些数字不代表什么¶

    这里只有一个消费者、一个队列、一个很小的消息体，以及一个在同一进程里的对端。它测的是一次投递 在这个 crate 里的开销，不是 ZeroMQ 能扛多少。这里的一行也不能拿去和另一个 Broker 公布的一行 比较：不同的传输在每条消息上做的事并不一样。

    每个循环放到线上的都是同样的三个帧：名字、头部、载荷。这是这个 crate 文档化的布局，也是外部对端 手写时照着写的那个布局。这个 crate 把三个帧都读出来，手写的循环只从第三个里取出载荷。所以这个 数字是这个 crate 的订阅、帧布局和发布者的代价，而不是多出那两个帧本身的代价。

    头部帧是空的。发送头部的服务，要在这里的数字之上，为这个 crate 的头部解析再付一次，每一次投递 都付。

    这个传输上没有任何确认。走这个 crate 的那两个循环仍然调用 ack，因为那正是确认该出现的位置， 而「不受支持」这个回答同样要等；裸循环则无处可调。为一个真会确认的 Broker 公布的行，测量窗口里 含着一次确认，而这一行一次也没有。

    这些数字是一台机器在某一天的快照。它们由人手工重测，测量期间机器只跑这一项：这一页要讲的差值， 比与其他任务共用的机器上的噪声还小。

    自己跑一遍¶

    just bench

    没有测试台要起。这条 recipe 跑完两个场景，然后把测到的结果写回 docs/benchmarks/results.json。 它要花几分钟，并且需要整台机器。消息条数不是固定的：一次试探运行会把它定下来，使得每一次被 测量的运行在所在机器上都不短于五秒。

    just bench-code

    这条 recipe 在 valgrind 下统计代码表，并重写同一份文档里的 code 部分。这里同样没有测试台要起： 服务绑定在回环地址上，对端是同一个进程里的一个套接字。它只需几秒，需要 valgrind 和基准测试运行器： cargo install --locked gungraun-runner --version =0.19.4。
