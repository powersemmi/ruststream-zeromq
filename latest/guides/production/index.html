    Running in production

    ZeroMQ has no server between services, so the deployment decides what a broker would otherwise decide: who listens, in which order services start, and how far a slow consumer buffers.

    Endpoints from the environment​

    • Macros
    • Manual
    src/main.rs
    use std::env;
    use std::num::NonZeroUsize;

    use ruststream_zeromq::queue::prelude::*;

    /// What the deployment decides: where the worker listens, where the sink is, and how far a
    /// subscription reads ahead of its handler.
    struct Settings {
        jobs: String,
        sink: String,
        read_ahead: NonZeroUsize,
    }

    impl Settings {
        fn from_env() -> Self {
            Self::from_vars(|name| env::var(name).ok())
        }

        fn from_vars(var: impl Fn(&str) -> Option<String>) -> Self {
            Self {
                jobs: var("JOBS_BIND").unwrap_or_else(|| "tcp://0.0.0.0:5555".to_owned()),
                sink: var("SINK_ADDR").unwrap_or_else(|| "tcp://sink:5558".to_owned()),
                read_ahead: var("ZMQ_READ_AHEAD")
                    .and_then(|value| value.parse().ok())
                    .unwrap_or(nonzero!(1000_usize)),
            }
        }
    }

    The endpoints and the read-ahead bound are the service's whole ZeroMQ configuration. Settings reads them from the environment the deployment sets, with a default for each. from_vars takes the lookup as a function, so a test passes its own values without touching the process environment.

    src/main.rs
    use serde::{Deserialize, Serialize};

    #[derive(Debug, PartialEq, Deserialize)]
    struct Job {
        id: u64,
        items: u32,
    }

    #[derive(Debug, PartialEq, Serialize, Outgoing)]
    #[outgoing(name = "results")]
    struct Done {
        id: u64,
        items: u32,
    }

    #[subscriber("jobs", reply)]
    async fn work(job: &Job) -> Done {
        tracing::info!(job.id, job.items, "job worked");
        Done {
            id: job.id,
            items: job.items,
        }
    }

    fn service(settings: Settings) -> RustStream {
        let sink = ZmqQueue::new(ZmqEndpoint::connect(settings.sink)).bindable();
        let results = sink.bind(Publish);
        let jobs = ZmqQueue::new(ZmqEndpoint::bind(settings.jobs)).read_ahead(settings.read_ahead);
        RustStream::new(AppInfo::new("worker", "0.1.0"))
            .with_broker(jobs, |b| {
                b.include(work).out_reply(results);
            })
            .with_broker(sink, |_b| {})
    }

    #[ruststream::app]
    fn app() -> impl App<State = ()> {
        service(Settings::from_env())
    }
    src/main.rs
    use serde::{Deserialize, Serialize};

    #[derive(Debug, PartialEq, Deserialize, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    struct Job {
        id: u64,
        items: u32,
    }

    #[derive(Debug, PartialEq, Serialize, JsonSchema)]
    #[schemars(crate = "ruststream::schemars")]
    struct Done {
        id: u64,
        items: u32,
    }

    // `#[outgoing(name = "results")]` by hand.
    impl OutgoingDestination for Done {
        type Form = FixedName;
        const DESTINATION: &'static str = "results";
    }

    impl MessageHeaders for Done {
        type Contract = NoHeaders;
    }

    struct Work;

    impl Handle<Job, Done> for Work {
        fn handle(
            &self,
            job: &Job,
            _outs: &(),
            _ctx: &mut Context<'_>,
        ) -> impl Future<Output = Result<Done, HandlerOutcome>> {
            tracing::info!(job.id, job.items, "job worked");
            ready(Ok(Done {
                id: job.id,
                items: job.items,
            }))
        }
    }

    fn service(settings: Settings) -> RustStream {
        let sink = ZmqQueue::new(ZmqEndpoint::connect(settings.sink)).bindable();
        let results = sink.bind(Publish);
        let jobs = ZmqQueue::new(ZmqEndpoint::bind(settings.jobs)).read_ahead(settings.read_ahead);
        RustStream::new(AppInfo::new("worker", "0.1.0"))
            .with_broker(jobs, |b| {
                b.include(subscriber("jobs", Work).reply().build())
                    .out_reply(results);
            })
            .with_broker(sink, |_b| {})
    }

    fn app() -> RustStream {
        service(Settings::from_env())
    }

    fn main() -> ExitCode {
        run_main(app)
    }

    The worker binds JOBS_BIND and dials the sink at SINK_ADDR. tcp://0.0.0.0:5555 listens on every interface; tcp://10.0.0.5:5555 listens on one. ipc:///run/jobs.sock is a Unix socket for services on one host. The side is part of the broker's type, so the deployment chooses the address and the code chooses the side.

    Startup order​

    A subscription that binds opens its port at startup, and a port another process holds fails the start with ZmqError::Endpoint. A subscription that dials waits for its peer to listen. The client retries the connection for up to 30 seconds, then the start fails with ZmqError::Endpoint, naming the address. So a service that dials may start before the peer it dials, as long as the peer listens within that window.

    A publisher on the bind side listens from the moment the service starts, so a peer that dials it connects before the first message. A publisher that dials attaches on its first publish. A send with no peer attached retries for five seconds, then fails with ZmqError::Send, naming the destination.

    Peer restarts​

    A publisher that dials its peer dials again once that peer has gone, and reaches it when it is back. A queue publisher learns of the loss from a failed send: the message sent into the dead connection is lost, the next publish returns ZmqError::Send, and the one after it dials anew. A fan-out publisher learns of it from its socket and dials on its next publish. A fan-out subscription that dials is dialed again by the client. A subscription that dials a PUSH peer keeps the connection it opened, so after that peer restarts it receives nothing until the service restarts too.

    Read-ahead and back-pressure​

    A subscription reads at most read_ahead deliveries ahead of its handler, 1000 by default. Past that bound it stops reading, the socket buffers fill, and the sender waits. So a slow handler slows the sender down instead of growing the memory of the service. On PUB/SUB the waiting sender is the publisher, held back by its slowest matching subscriber. The bound is set per broker, here from ZMQ_READ_AHEAD.

    Security​

    The client negotiates the NULL mechanism: peers connect without credentials, and traffic travels as plain bytes. A service therefore runs inside a network it trusts, or inside a tunnel: a VPN, WireGuard, or an SSH tunnel. The generated AsyncAPI document reports each endpoint's host and port without credentials (Server).

    Shutdown​

    On shutdown the service stops its subscriptions and closes its sockets. A publisher handed out earlier then fails with ZmqError::NotConnected instead of sending into nothing. A queue publish is safe to cancel. A fan-out publish, a reply and a request are not, so give up through a timeout, not a select! arm (Cancellation).

    Testing the configuration​

    The tests build Settings with from_vars. One checks the defaults of an empty environment. The other starts the configured service under TestApp::start and checks that a result reaches the sink. The in-process mode opens no socket, so the addresses need not exist.
