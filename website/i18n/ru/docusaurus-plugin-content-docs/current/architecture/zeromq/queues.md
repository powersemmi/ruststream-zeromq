# Очереди

Клиент `zeromq` не держит очереди сообщений: отправка пишет кадры в соединение узла, а то, что ещё
в пути, хранят буферы сокетов ядра.

<Diagram name="queues" words={words} />

Отправка PUSH берёт следующий по очереди узел и пишет кадры в соединение этого узла. Отправка
заканчивается, когда кадры записаны, поэтому узел, который читает медленно, заставляет отправку
ждать.

Сокет PULL, когда у него запрашивают сообщение, читает по одному сообщению от каждого
подключённого узла по очереди. До тех пор кадры остаются в буферах ядра, на этой стороне и на
стороне отправителя.

Отправка PUB пишет сообщение в соединение каждого подписчика с совпавшим фильтром, одно за другим.
Поэтому самый медленный из этих подписчиков задерживает издателя, и из-за медленного подписчика
ничего не теряется. Сообщение, которому не подошёл ни один фильтр, отбрасывается без ошибки.

libzmq, библиотека на C, которой пользуется большинство других языков, работает иначе. Там у
каждого соединения своя очередь, по умолчанию на 1000 сообщений (предельный размер очереди,
`SNDHWM` и `RCVHWM`). Когда очередь заполнена, PUB отбрасывает сообщение, а PUSH блокирует
отправку. У клиента `zeromq` нет ни такой очереди, ни такой настройки: параметры сокета - это
идентичность узла и таймаут подключения.

Насколько далеко вперёд читает подписка этого крейта, ограничивает собственный канал крейта
глубиной [`read_ahead`](../../components/subscriptions/read-ahead.md). Его показывает страница
[Обратное давление](../backpressure.md).

Числа libzmq взяты из [zguide](https://zguide.zeromq.org/docs/chapter2/) (раздел «High-Water
Marks»). Поведение клиента описано по исходному коду
[`zeromq` 0.6](https://docs.rs/zeromq/0.6.0/zeromq/).
