# 基准测试 { #benchmarks }

这个 crate 位于 `zeromq` 客户端和你的服务之间：一个产出消息的订阅、一份文档化的帧布局、一个把它
写出去的发布者。框架的运行时又在这之上。这一页说明这两层各自花了多少，参照物是同样的活用客户端
手写一遍。

每个场景在同一个进程里跑三遍，三个循环之间只差一件事：由什么来搬运消息。

- **裸客户端** - 直接驱动 `zeromq` 套接字：绑定、接收、解码。
- **ruststream-zeromq** - 这个 crate 的订阅、它产出的消息、它的 `ack` 和它的发布者，由基准测试
  里的一个循环来驱动：没有处理器、没有应用、没有分发。
- **RustStream 服务** - 用户会写的那整个服务，`#[subscriber]` 加上应用，跑在同一个 crate 上。

「crate 的开销」是第二列对第一列：这个 crate 在它所包装的套接字之上要花多少，这个仓库要为这个
数字负责。「总开销」是第三列对第一列，于是两者之差就是运行时。运行时属于核心 crate，它在自己的
仓库里以每条消息的指令数和分配数来度量；这两列补上的是运行时在这一个传输上的代价。

其余一切都保持相同：套接字的模式、套接字选项、线上的三个帧、解码成同一个类型、载荷字节、tokio
运行时和构建。这套流程属于框架本身，写在
[RustStream 基准测试页](https://powersemmi.github.io/ruststream/latest/zh/benchmarks/#methodology)
上；这一页公布它在这台机器上得出的结果。

## 这一行里没有 Broker { #there-is-no-broker-in-this-row }

框架里其他每个 crate 都拿自己和一台服务器相比：起一个容器，客户端连上去，这一行说的是这个 crate
在那个客户端之上多付了多少。ZeroMQ 没有服务器。对端彼此直接讲话，所以每个循环的另一侧都是同一个
进程里的一个套接字，没有什么要起、也没有什么要停。

这让这一行回答的是另一个问题，而不是把原来的问题答得更快或更慢。路上没有服务器的传输，每条消息
都很便宜，于是这个 crate 自身的活在总数里占的比重比别处都大。把这里的百分比和别的 crate 放在
一起看，只在记住这一点的前提下才有意义。

## 数字 { #the-numbers }

交错各轮的中位数，括号里是观察到的离散范围。速率那几列越大越好。

两个场景都是 PUSH/PULL 模式，跑在这个 crate 允许的两种传输上：回环地址上的 `tcp://` 和
`ipc://`。它们只差在一条消息走过内核的路径，别的都一样，所以两个放在一起就能看出其中有多少
代价落在套接字上。

标为「无法区分」的开销，小于它所比较的那两列各自多次运行之间的离散范围。低于这个范围的数字读
起来像是从未测到过的精度，所以不公布。

这里没有哪一行带着「受传输限制」的标记，这是模式本身的性质，不是机器的性质。这个标记说的是：一次
投递的大部分时间都花在等传输上，它上面的活就做在这段本来就要付的等待里面。PUSH/PULL 不给一次
投递任何可等的东西：消费者从流里读帧，什么也不回送，没有轮询、没有拉取、也没有确认，所以一次
投递要花零次往返，这个标记无从谈起。

下面和机器一起公布的往返时间，是同一个传输上两个对端之间一次交换的代价，用一对 REQ/REP 套接字在
三个循环之外测得。把它乘以上面那个零，再和每条消息的时间比一比：标记就是从这个算式来的，你可以
自己验算。

同一次运行的机器可读形式在
[`benchmarks/results.json`](https://powersemmi.github.io/ruststream-zeromq/latest/benchmarks/results.json)，
框架的站点用它拼出跨 Broker 的汇总表。

## 机器 { #the-machine }

<div id="benchmark-environment"></div>

`zeromq` crate 既不提供高水位，也不提供缓冲区设置：一个套接字只有对端身份和连接超时，别的都
没有。所以每个循环都用默认选项打开套接字，限制队列的是传输自己的缓冲区。再没有别的可调，所以
除了传输本身，也没有别的套接字配置可以公布。

构建标志和数字一起公布，因为它们会改变这些数字。用 `-C target-cpu=native` 构建出的二进制给出的
结果，换一台机器就复现不了，所以这条 recipe 在构建前先把这个变量清空。

## 这些数字不代表什么 { #what-they-do-not-mean }

这里只有一个消费者、一个队列、一个很小的消息体，以及一个在同一进程里的对端。它测的是一次投递
在这个 crate 里的开销，不是 ZeroMQ 能扛多少。这里的一行也不能拿去和另一个 Broker 公布的一行
比较：不同的传输在每条消息上做的事并不一样。

每个循环放到线上的都是同样的三个帧：名字、头部、载荷。这是这个 crate 文档化的布局，也是外部对端
手写时照着写的那个布局。这个 crate 把三个帧都读出来，手写的循环只从第三个里取出载荷。所以这个
数字是这个 crate 的订阅、帧布局和发布者的代价，而不是多出那两个帧本身的代价。

头部帧是空的。发送头部的服务，要在这里的数字之上，为这个 crate 的头部解析再付一次，每一次投递
都付。

这个传输上没有任何确认。走这个 crate 的那两个循环仍然调用 `ack`，因为那正是确认该出现的位置，
而「不受支持」这个回答同样要等；裸循环则无处可调。为一个真会确认的 Broker 公布的行，测量窗口里
含着一次确认，而这一行一次也没有。

这些数字是一台机器在某一天的快照。它们按需重测，从不放进 CI：共享 runner 的噪声比这一页要讲的
差值还大。

## 自己跑一遍 { #running-it-yourself }

```bash
just bench
```

没有测试台要起。这条 recipe 跑完两个场景，然后把测到的结果写回 `docs/benchmarks/results.json`。
它要花几分钟，并且需要整台机器。消息条数不是固定的：一次试探运行会把它定下来，使得每一次被
测量的运行在所在机器上都不短于五秒。
